## Critical

- File: `mini-db/src/main/java/cn/zhangyis/minidb/storage/catalog/ddl/DdlLogManager.java:173` | Severity: critical | Category: Diff | Description: the new "force before commit" path is not failure-atomic. `appendRecordAndForce()` and `rewriteAllRecordsAndForce()` mutate live DDL-log pages, call `bufferPool.flushPage()` page-by-page, and only then `commit()`. If any flush or the final `sync()` fails after an earlier page was already written, the method throws, but `MiniTransaction.rollback()` does not restore page bytes. That can leave a torn DDL-log chain partly on disk and partly still dirty in memory, which is exactly the kind of recovery-path corruption this code is meant to prevent. | Suggested fix: do not rely on rollback to undo pre-commit page mutations. Either restore a commit-then-force design with an explicit durability barrier that is safe for this module, or add a separate failure-safe persistence path and regression tests that inject flush/sync failures during append and compaction.

## High

- File: `mini-db/src/main/java/cn/zhangyis/minidb/storage/transaction/dml/TransactionalDml.java:847` | Severity: high | Category: Diff | Description: `updateRollPtr()` writes directly into `page.getBuffer()` and only calls `mtr.markDirty(page)`. That bypasses MTR modification tracking, so no redo record is generated for the new `ROLL_PTR`, and the write also happens without an explicit frame X-latch. A crash can therefore persist an undo-compaction side effect in memory without a matching redo record, breaking MVCC version-chain recovery. | Suggested fix: switch this path back to an X-latched `BufferFrame` update and record the change through `MiniTransaction` write helpers or equivalent redo-aware APIs.

- File: `mini-db/src/main/java/cn/zhangyis/minidb/storage/transaction/lock/LockRequestQueue.java:175` | Severity: high | Category: Diff | Description: `cancelWait()` removes matching entries from both `waitingList` and `grantedList`. Combined with `LockManagerImpl.waitForLock()`'s timeout/deadlock cleanup, a request that is granted just after the caller's last `isGranted()` check can still be deleted from `grantedList` and then reported as a timeout or abort. That drops a real grant on the floor and reopens the grant-vs-timeout race. | Suggested fix: make cancellation an in-lock `WAITING -> ABORTED` transition only, and never remove `GRANTED` requests from `cancelWait()`. Add a boundary-race test that grants a waiter exactly as its timeout path fires.

- File: `gradlew` | Severity: high | Category: Holistic | Description: the repository includes Gradle wrapper scripts, but the wrapper runtime is missing. `./gradlew` fails immediately with `ClassNotFoundException: org.gradle.wrapper.GradleWrapperMain`, so a clean checkout cannot run the build or test entrypoint that contributors and agents would reasonably expect to use. | Suggested fix: commit `gradle/wrapper/gradle-wrapper.jar` and `gradle/wrapper/gradle-wrapper.properties`, then verify `./gradlew :mini-db:test` works from a clean clone.

## Medium

- File: `mini-db/src/main/java/cn/zhangyis/minidb/storage/DatabaseBootstrap.java:186` | Severity: medium | Category: Diff | Description: `DatabaseBootstrap` is documented as supporting "首次启动", but `ensureSystemSpaceOpen()` only attempts `openTablespace()` and never creates the system tablespace when the data directory is empty. On a true first boot the class fails before catalog initialization can run, so the implementation does not match the API contract or class-level documentation. | Suggested fix: detect the missing system tablespace and create it on first start before catalog bootstrap, then add an empty-directory regression test for that path.

- File: `mini-db/src/test/java/cn/zhangyis/minidb/storage/catalog/CatalogManagerPhase4Test.java:274` | Severity: medium | Category: Diff | Description: the new DDL-recovery tests simulate restart by calling `catalogManager.close()`, `bufferPool.close()`, and `diskManager.close()` before reopening. That validates clean restart, not crash recovery, so it would not catch the DDL-log durability regression above because the close path flushes state after the fact. | Suggested fix: add crash-style recovery tests that reopen the files without any clean close/flush step, or inject disk failures around `appendIntentAndForce()` and compaction to verify durability at the point the API claims it.
