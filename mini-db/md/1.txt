并发优化要分两层看：(A) commit/flush 的 group commit 并发，以及 (B) redo 子系统内部的并发写入/推进水位。你这份蓝图现在主要瓶颈会落在：等待唤醒、锁竞争、以及“连续区间推进”三个点上。下面给一组可以直接落到你设计里的并发优化方案（按收益/复杂度排序）。

1) 提交侧并发（Group Commit 的核心并发优化）
1.1 只允许一个 leader 触发 fsync（避免重复 fsync）

并发提交最常见退化：多个提交线程同时把 flusher 唤醒/甚至直接 fsync，导致批量被打碎。

做法：

flush_leader 用 CAS 或 tryLock 选举

follower 只登记 commit_lsn 并 park() 等待

leader 计算 flush_target（通常取当前 write_lsn），执行一次 fsync，然后一次性唤醒满足条件的 follower

**收益：**避免“多 fsync + 小批次”，P99 延迟更稳，吞吐上升。

1.2 用“按 LSN 的 notifier”替换 signalAll（避免惊群）

如果你现在是 signalAll() 唤醒所有等待 flush 的事务，提交并发上来后会出现“惊群”：大量线程被唤醒又立刻睡回去。

做法：

维护 flushed_lsn 单调递增

等待者只登记自己的 target_lsn

notifier 每次推进 flushed_lsn 后，只唤醒 target_lsn <= flushed_lsn 的那部分（可用分桶/队列/最小堆）

MVP 版本（简单但有效）：

ConcurrentLinkedQueue<Waiter> + “循环扫描唤醒满足条件的”（批量提交时扫描次数可控，因为 flush 次数少）

进阶版本（更强）：

LSN 分桶（例如按 4KB/8KB bucket）保存 waiters，推进时只扫少量 bucket

2) redo buffer 并发写（用户线程并发写 log buffer 的优化）

你要并发优化，最终绕不开 MySQL 8 的核心思想：reserve（分配空间）并发、copy 并发、writer 只写连续完成区间。

2.1 reserve 用原子 fetch_add（无大锁）

sn = global_sn.fetch_add(len) 预留独占空间（len 是 payload bytes）

用户线程只往自己区间 copy，不互斥

**注意：**这会产生 holes（有人预留了但还没写完），writer 不能直接按 global_sn 写盘。

2.2 用 recent_written（或你自己的“完成表”）解决 holes

**目标：**让 writer 找到“从某个起点开始连续完成”的最大前缀，推进 buf_ready_for_write_sn。

实现选择：

MVP：每个 reserve 段写完后登记到 completed_ranges（比如 lock-free ring + slot=sn/len），writer 顺序消费连续段

进阶：link_buf（slot 环形数组）：

index = (sn / SLOT_BYTES) % SLOT_COUNT

slot 里记录“该 slot 覆盖的 sn 段是否完成/完成到哪里”

writer 只要沿 tail 推进，直到遇到未完成 slot

**收益：**高并发下避免“writeReadySn = max(sn)”这种错误推进；同时减少锁争用。

2.3 关键对齐：内部水位统一用 SN，格式化阶段才转 LSN

并发优化的前提是“推进水位正确”。并发写 log buffer 时建议：

current_sn / ready_sn / write_sn / flushed_sn 全部用 sn（payload 单位）

sn→lsn 只在 formatter/落盘 offset 计算时做

这样不会因为 block header/trailer 开销导致推进错位。

3) writer/flusher 线程并发（锁、IO、系统调用优化）
3.1 writer 线程：批量格式化 + 批量 write（减少 syscalls）

writer 从 buf_ready_for_write_sn 到 write_sn 批量取一段（例如 64KB~1MB）

统一 format 成 log blocks，再 FileChannel.write(ByteBuffer[])（gather write）

尽量避免每个 block 一个 write

3.2 flusher 线程：只 fsync 到 flush_target（批次上界明确）

每轮 fsync 前固定 flush_target_lsn/sn（例如取当时 write_sn）

fsync 完后一次推进 flushed_sn=flush_target_sn

notifier 唤醒 commit_lsn <= flushed_lsn

**收益：**fsync 次数最少、唤醒次数最少，符合 group commit 的吞吐目标。

3.3 条件变量/park 替代 sleep 轮询

轮询（sleep 1ms/10ms）在并发写入下会造成：

延迟抖动

多余 wakeup

建议：

writer：当 buf_ready_for_write_sn 没变化时 park，由用户线程“发布完成段”后 unpark 或 signal

flusher：当 write_sn 没变化且没有等待者时 park

4) checkpoint/刷脏 并发（避免把 redo 并发收益抵消）
4.1 checkpoint 安全边界：避免推进过头造成 stall

并发系统里 checkpoint 的“可推进 lsn”要受两类约束：

最老脏页 LSN（flush list 的 oldest）

dirty pages 已登记边界（类似 recent_closed 的连续边界）

如果你暂时不做 recent_closed，至少要保证：

flush list 能稳定给出 oldest_lsn（按 oldest_modification_lsn 有序或有最小值结构）
否则很容易出现 redo free space 计算抖动，触发不必要的 stall。

4.2 反压（backpressure）要作用在 reserve 阶段，而不是 commit 阶段

redo 空间不足时：

最好在 reserve 时就阻塞（或降速），避免线程都跑到 commit-wait 才集体卡死

并发下这能显著降低 tail latency

5) 一份“从易到难”的落地路线（建议你按阶段加进蓝图）
Phase A（低成本，高收益）

leader/follower group commit（只有一个触发 fsync）

notifier 替代 signalAll（按 target_lsn 唤醒）

writer/flusher 用 park/Condition 替代 sleep

writer 批量写（减少 syscalls）

Phase B（中成本，吞吐上台阶）

reserve 用 atomic fetch_add（并发写 log buffer）

completed_ranges 或简化 recent_written（解决 holes，推进 ready_sn）

sn 水位统一、formatter 才做 sn→lsn

Phase C（高成本，接近 MySQL 8）

recent_written + recent_closed（checkpoint 可推进边界更准）

更精细的 write-ahead buffer / partial block 处理

checkpoint governor（按 redo free space 自适应刷脏力度）
